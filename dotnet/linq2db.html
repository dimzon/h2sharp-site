linq2db in progress

The linq2db provider lives in its own repository, dimzon/h2sharp-linq2db — written from scratch against linq2db's public API and the engine's public API. Unlike the Entity Framework Core provider, this one is not a fork of another provider.

What it generates is H2's SQL, checked against H2's frozen documentation and against the reference engine on the JVM. The capabilities it declares are H2 2.5's, not the engine's current ones: a provider that declared the engine's abilities would be describing a database that does not exist.

Using it

using LinqToDB;
using LinqToDB.DataProvider.H2Sharp;

await using var db = H2SharpTools.CreateDataConnection("jdbc:h2:mem:mydb");

var rows = await db.GetTable<Row>()
    .Where(r => r.Price > 10m)
    .OrderBy(r => r.Id)
    .ToListAsync();

The public API is H2SharpTools.GetDataProvider, CreateDataConnection, H2SharpProvider and H2SharpVersion. It is built for .NET 8 and .NET 10, against the released linq2db 6.5.0.

The connection string

The engine's ADO layer takes a JDBC URL; the .NET world spells the same thing Data Source=mem:mydb. Both are accepted, and the translation is one call if you want to see it:

What is writtenWhat the engine opens
jdbc:h2:mem:mydbjdbc:h2:mem:mydb
Data Source=mem:mydbjdbc:h2:mem:mydb
Data Source=mem:mydb;MODE=PostgreSQLjdbc:h2:mem:mydb;mode=PostgreSQL
var url = H2SharpConnectionString.ToUrl("Data Source=mem:mydb;MODE=PostgreSQL");
// jdbc:h2:mem:mydb;mode=PostgreSQL

The name of an array is the name of the type of its elements and the word ARRAY after it — integer ARRAY, varchar ARRAY. H2 does not know the brackets of PostgreSQL (integer[]). The mapping schema knows the array types, so the name does not have to be said by hand; it can still be, for a type the schema does not know.

H2's functions for an array are H2SharpSpecificExtensions.ArrayAppend, ArrayCat, ArrayContains, Cardinality and ArrayLength — the functions of H2 2.5: ARRAY_APPEND, ARRAY_CAT, ARRAY_CONTAINS, CARDINALITY and ARRAY_LENGTH. The engine reads the ARRAY type, its literals, the functions and UNNEST now, so a table with such a column works end to end.

What it generates

Identifiersalways quoted, the way H2 documents it: an unquoted identifier folds to upper case and a quoted one does not
TypesH2's own: varchar, char, numeric, varbinary, uuid, json, clob, blob, timestamp, time, boolean, smallint, integer, bigint, real, double
PagingLIMIT n / OFFSET n, with the count as a parameter
ConcatenationCONCAT, which H2 has
Parametersnamed $name (case-sensitive), which the ADO layer rewrites into $N before the statement is parsed — @name is an H2 session variable and :name plain syntax, neither is a parameter
Table aliaswithout the AS: the grammar allows both spellings, and the bare one is the shorter
Type castCAST(x AS y) — H2 2.5 also reads the PostgreSQL-style x::y and the port does too, but the provider writes the standard form

The data context

DataConnection is the whole API; DataContext is the same thing with a type that knows its tables. Both work with the async methods and both take part in a transaction. The last statement the provider sent is on the connection — db.LastQuery — and it is put there when the statement is sent, so a statement the engine refuses while it runs is there too; a statement it refuses to read never reaches the database and is not on the connection.

Port gaps it is waiting on

Listed in the provider's own docs/DIVERGENCES.md, where each one says who has to fix it — here they are all port defects, not limits of H2:

GapSymptom
A catalogue column without a collationthe collation column is empty where H2 2.5 gives the collation of the database; the catalogue's name is now the database's name
DB_CLOSE_DELAY and a file databasethe store itself is in the port and its format is H2 2.5-compatible, but a session does not open a file database — and a pooled connection takes the database with it
The engine's catalogue from the ADO layerH2Connection.Session is internal, while the schema's table list wants a SessionLocal

How the first bug was found

Worth telling, because it is the method the whole project follows: an INSERT wrote the column names instead of the values. The cause was not in the provider's own code but in linq2db's base Convert, which writes a parameter's name as it is — because the prefix is each provider's business: PostgreSQL and Oracle write :, H2 must write @. It was found with an instrumented local copy of linq2db's core, with the insert expression and the generated SQL printed under LINQ2DB_DEBUG_SQL=1. A published package cannot be instrumented, so the build moved to a local copy of the sources, with a property to point at it — building against the released package stays possible.
