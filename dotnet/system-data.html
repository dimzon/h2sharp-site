System.Data / ADO.NET available

A standard ADO.NET provider in H2Sharp.Data (System.Data.Common). It is measured against the inherited AdoNet.Specification.Tests conformance suite and by a green Dapper flow — not against itself.

In-memory and file databases. The provider opens mem: databases and file ones — Data Source=C:/data/demo opens demo.mv.db in the format the reference H2 reads back. Async OpenAsync still completes synchronously, and DB_CLOSE_DELAY is not there yet: an in-memory database is dropped when its last connection closes.
Gate (phase 8) — closed twice over: DapperSmokeTests drives an in-memory database end to end over IDbConnection (open → create → insert → update → select → delete), and the inherited AdoNet.Specification.Tests suite is 293 of 293 green. Source: src/H2Sharp/Data/, tests: tests/H2Sharp.Data.Tests/.

Connection strings

The classic ADO.NET spelling — jdbc:h2: is no longer accepted by H2Connection (it lives only in the test infrastructure for the Java oracle). Unknown keys and credentials (USER/PASSWORD/User ID/Password) are rejected rather than ignored.

Data Source=mem:mydb;Storage=Memory            // in-memory database keyed "mydb"
Data Source=file.db;Storage=File;Mode=Regular   // file database in the reference H2 format
Storage=Memory                                 // unnamed in-memory database

H2ConnectionStringBuilder parses the classic string into a typed ConnectionInfo (StorageKind, DataSource, Mode, ConnectionOptions); ToConnectionInfo() and LoadFrom() are the two conversion points.

Recommended: H2DataSource (DbDataSource)

A data source owns the database: it creates it on first open, keeps it alive while the data source lives (close delay -1), and hands out connections that share it. Raw H2Connection instances are self-contained and close their own database. Prefer the data source for pooling, triggers, trace and event listeners.

var ds = H2ProviderFactory.Instance.CreateDataSource("Data Source=mem:mydb;Storage=Memory");
await using var con = ds.CreateConnection();
con.Open();

// or build it by hand:
var ds2 = new H2DataSourceBuilder("Data Source=mem:mydb;Storage=Memory")
    .ConfigureExtensions(e => e.RegisterUdf(...))
    .Build();

Registration

services.AddDbConnectionFactory<H2ProviderFactory>(_ => new H2ProviderFactory());
// or construct directly:
await using var con = new H2Connection("Data Source=mem:mydb;Storage=Memory");

Transactions

// explicit transaction
using var tx = con.BeginTransaction();
con.Execute("INSERT INTO PERSON VALUES($Id, $Name)", new { Id = 2, Name = "Grace" });
tx.Commit();  // or tx.Rollback()

// ambient transaction (TransactionScope / System.Transactions)
using var scope = new TransactionScope();
con.EnlistTransaction(Transaction.Current);
con.Execute("INSERT INTO PERSON VALUES($Id, $Name)", new { Id = 3, Name = "Ada" });
scope.Complete();

EnlistTransaction switches the session out of auto-commit; the engine transaction is kept by the enlistment until the ambient transaction completes, so the connection may be closed before it commits. A second transaction on the same connection is refused.

Named parameters

A named parameter is spelled $name, and the name matches case-sensitively — $Id and $id are different parameters. The rewrite lives in the command layer: the text the engine sees carries ?, ?N and $N, with $name resolved to its index before the statement is prepared. Two spellings are deliberately not parameters: @name is H2's session variable and :name is plain SQL syntax (including JSON_OBJECT(k : v)). Dapper understands $ out of the box.

Not implemented yet

Honest list — these throw or are absent, by design at this stage:

  • ChangeDatabase — not supported: the database is named by the connection string at open.
  • Async OpenAsync — it completes synchronously; file opens do I/O, and then it becomes truly asynchronous.
  • DB_CLOSE_DELAY — SET DB_CLOSE_DELAY works, and a data source owns its database with close delay -1 so it outlives a connection; a bare connection still drops its database on close.
  • H2CommandBuilder refuses command generation — it needs the schema machinery behind GetInsertCommand and friends; H2DataAdapter.Update needs commands supplied by hand.
  • No data-source enumerator — CanCreateDataSourceEnumerator is false.

GetSchema() over INFORMATION_SCHEMA is implemented (MetaDataCollections, Tables, Columns, …), and CanCreateBatch is true (H2Batch). H2DataReader.GetSchemaTable() works too.
