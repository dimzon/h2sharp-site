EF Core in progress

The Entity Framework Core provider lives in its own repository, dimzon/h2sharp-efcore — a fork, and its own history and release cycle are separate from the engine's.

What it is: a fork of EFCore.PG (Npgsql's provider for PostgreSQL), with PostgreSQL's surface replaced by H2's — the type mappings, the migrations SQL generator, the connection and the DDL are H2's. The point of forking rather than writing a provider is to keep EF Core's own specification suite as the measure: the tests are inherited from EF Core, not written for H2.

Value generation

The reference has no INSERT … RETURNING — it refuses the clause — and no SCOPE_IDENTITY(), no IDENTITY() and no LAST_INSERT_ID(). The Npgsql model of "insert, then read the key back" transfers as the form H2's grammar has: the row the insert made is read through FINAL TABLE, so the insert is written as SELECT "Id" FROM FINAL TABLE (INSERT INTO …). The port reads both the identity DDL and FINAL TABLE, so the value comes back. A sequence (NEXT VALUE FOR, CURRENT VALUE FOR) is the other way, and the port reads that too.

Strings

A string is a CHARACTER VARYING in H2 2.5 — without a length it takes the maximum, so a string of any size fits. CHARACTER LARGE OBJECT is a different thing: H2 keeps such values out of memory and streams them. The port has the storage of a large object but not the way out of it into a result, so such a column cannot be read back yet.

Scaffolding

dotnet ef dbcontext scaffold "Data Source=mem:mydatabase" H2Sharp

The provider's part is written — it reads INFORMATION_SCHEMA the way H2 2.5 keeps it — and it refuses with a message naming the missing engine feature rather than returning an empty model: an empty model would be indistinguishable from an empty database, and every migration made from it would try to recreate tables that are there. What is still missing is CREATE SCHEMA: the scaffolding test makes a schema of its own before it asks about the tables in it, and the nine scaffolding tests are marked as the engine's defects until it does.

H2's own functions

ILike is an operator in H2, not a function, so the text it stands on has to be a column. LOCATE takes the substring first — the other way round from the function of the SQL standard.

Window functions

H2 2.5 has them — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE, NTILE, PERCENT_RANK, CUME_DIST — but Entity Framework Core 9 does not translate them into a query, so there is nothing for the provider to write. A provider cannot add what the framework never asks for.

The range table

H2 has a table function giving a row per number of a range: SYSTEM_RANGE(min, max[, step]). The engine reads it, and the provider asks for it the way a caller asks for any statement it writes itself — through FromSqlRaw, over an entity type without a key. The step goes to the start and the range stops at the end, so SYSTEM_RANGE(1, 10, 2) gives 1, 3, 5, 7, 9, as the reference gives. The engine reads the range table as a plain source: a derived table around it is not read yet, and EF Core's own queries of an entity with a key put the raw SQL into a derived table, so a keyless type is the one that works.

The provider is built for .NET 8 and .NET 10, and so is the engine under it. While the engine is unfinished, the providers are pre-release: the engine is a dependency of both, and a stable package cannot depend on a pre-release one.
